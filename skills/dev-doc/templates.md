# 文件模板与期望

模板是骨架不是清单：**没有内容的章节直接删掉，不要留空标题占位。**

每个文件下的「期望」描述这个文件读起来应该是什么样子。怎么维护成这样，自己判断。

所有文件带极简 frontmatter，`updated` 覆盖写。

---

## requirements.md

```markdown
---
plan: <plan-slug>
status: 进行中 | 已完成 | 已搁置
updated: YYYY-MM-DD
---

# <任务名>

## 问题

<现在哪里不对、缺了什么、谁因此受影响。3-8 行。必须让人看懂"不做会怎样"。>

## 目标

- <完成后可观察到的结果>

## 边界

- 不做：<明确排除的范围> — 原因：<一句话>

## 约束

- <必须遵守的：兼容性 / 性能 / 依赖 / 平台 / 既有约定 / 时间> → F-n

## 验收标准

- **AC-1** <可判定为 yes/no 的条件>
- **AC-2** <...>

## 未确认假设

- <你从代码或上下文推断、但用户未确认的前提> — 猜错的后果：<...>
```

**期望**

- 「问题」只有现状与代价，没有解法 — 解法属于 design.md
- 「目标」是结果不是动作 — 正例 `断线重连后客户端房间状态与服务端一致`；反例 `增加 reconnect 方法`
- 「边界」比目标更能防止范围蔓延，是留给后来者的护栏，值得认真写
- 每条 `AC` 能被测试或人工一次判定，不出现"性能良好"这类不可判定项
- 「未确认假设」里只有推断，正文里只有确认过的事实；事实的**依据**在 findings.md，这里只写结论并挂 `→ F-n`，不贴 `file:line`、不写调查过程

## findings.md

```markdown
---
plan: <plan-slug>
updated: YYYY-MM-DD
---

# 查明的事实

## 用户告知

- **F-1** <一句现在时陈述> — 依据：用户 YYYY-MM-DD 告知「<原话片段，可选>」— 支撑：AC-2、D-1

## 自行查明

- **F-2** <一句现在时陈述> — 依据：`path/to/file.go:120-140` — 支撑：D-3
- **F-3** <一句现在时陈述> — 依据：测试 `x_test.go:TestRetry` 运行结果 / 日志 <id> — 支撑：R-1
```

**期望**

- 两节**按来源分开**是给人看的：「用户告知」人要核对的是 agent 有没有转述走样，「自行查明」人要核对的是 agent 有没有读错代码——两种核对动作不同，混在一起就都做不了。对 agent 自己，「用户告知」是接手时必读的，因为它无法从代码重建
- 一条 finding 是一句**现在时、可验证**的陈述加一个依据指针。没有指针的不是 finding，是推断，去 requirements 的「未确认假设」；假设被验证后移过来，两处不并存
- 归节看**来源**，不看强弱：用户说的进「用户告知」，即使后来在代码里核实了也留在原节、把代码指针追加到依据里——人要能一眼看出哪些前提是自己给的
- 「支撑」为空的条目要么很快被引用，要么在收尾时删除；**无引用即删除**是这个文件不变成调查日记的唯一护栏
- 结论不写在这里：约束在 requirements、决策在 design，这里只有它们的依据。review 问题的证据留在 `R-n` 自己的「证据」字段，不搬过来
- 依据被代码本身承载后（加了注释、写了测试），压成一行指针或删除

## design.md

```markdown
---
plan: <plan-slug>
updated: YYYY-MM-DD
---

# <任务名> 设计

## 方案概述

<一段话讲清整体思路：用什么方式解决 requirements 中的问题。>

## 待拍板

<agent 已经选定、正按它实施、但用户还没认可的决策。用户点头后整条搬到「已确认」，编号不变。>

### D-2 <决策标题>

- **决策**：<当前采用的做法>
- **理由**：<为什么是它> → F-n
- **取舍**：<放弃了什么 / 代价是什么>
- **关联**：AC-1、AC-3

## 已确认

### D-1 <决策标题>

- **决策**：<当前采用的做法>
- **理由**：<为什么是它> → F-n
- **取舍**：<放弃了什么 / 代价是什么>
- **关联**：AC-1、AC-3

## 结构与流程

<只描述与本任务相关的部分，用 ASCII 图或 mermaid；ASCII 图内一律用英文标注。已落地的模块直接用文件路径索引，不复述其内部实现。>

## 接口与数据契约

| 契约 | 形态 | 落点 |
|------|------|------|
| <名称> | <未落地：写目标形态；已落地：写"见落点"> | `path/to/file.ts:symbol` |

## 影响面

- <受影响的模块 / 兼容性 / 数据迁移 / 上下游调用方>

## 已否决方案

- <方案> → <否决理由>

## 未决问题

- <还没想清楚的设计点> — 卡点：<在等什么信息或决定>
```

**期望**

- 一个主题只有一条 `D-n`，读者不需要判断哪条才是当前有效的
- 决策按**用户是否认可**分两节：默认进「待拍板」，只有用户在对话里明确认可、或方案本来就是用户提的，才进「已确认」；"用户没反对"不算认可。分节是给人读的：接手或 review 时一眼看出哪些是自己签过的、哪些是 agent 替自己选的
- 「待拍板」不阻塞实施——agent 按它继续干；用户点头后整条搬到「已确认」，编号不变；被否则移到「已否决方案」带理由。它和「未决问题」的边界：待拍板是已经选了一个在等点头，未决问题是还没选
- 「理由」写判断，判断所依据的事实指向 `F-n`；理由里出现 `file:line` 或"我看了 X 发现 Y"，就是证据写错了地方
- 「已否决方案」存在的唯一理由是**防止后来者重提同一个被否掉的方案**，所以每条都要带否决理由；它是全文档唯一允许保留"走过的弯路"的地方
- ASCII 图内用英文 — 正例 `client --seq--> server --delta--> client`；反例 `客户端 --序号--> 服务端`（CJK 字符宽度不固定会把图撑歪）。中文解释写在图外

## tasks.md

```markdown
---
plan: <plan-slug>
updated: YYYY-MM-DD
---

# 待办

## 进行中

- [ ] <正在做的事> — 已完成到：<具体位置/状态> / 下一步：<具体动作>

## 阻塞

- <卡住的事> — 在等：<用户答复 / 外部依赖 / 另一个任务>

## 待办

- [ ] <还没开始的事> → D-2
- [ ] <...>
```

**期望**

- 文件里**只有还没做的事**，且随任务推进趋向空 — 没有勾选留档、没有「已完成」章节、没有日期流水
- 「进行中」那条的"下一步"是**具体动作**，不是"继续实现 X"。上下文丢失后这是最值钱的一行

## implementations.md

```markdown
---
plan: <plan-slug>
updated: YYYY-MM-DD
---

# 实施记录

## 改动清单

### C-1 <改动单元名>

- **做了什么**：<行为层面 1-3 句：现在的代码具备什么能力 / 行为如何>
- **落点**：`path/to/a.ts:ClassName.method`、`path/to/b.ts`
- **关联**：D-1、AC-2

## 关键落点地图

| 文件 | 在本任务中的职责 |
|------|----------------|
| `path/to/x.ts` | <一行> |

## 与设计的偏差

- <偏离点> — 原因：<为什么> — design.md 已同步：是 / 否

## 遗留

- <有意留下的技术债或未覆盖场景> — 原因：<为什么现在不做>
```

**期望**

- **没有代码片段、diff、commit 号**。落点写到 `文件:符号`，代码本身去读代码
- 描述行为不描述实现步骤 — 正例 `重连时用本地 seq 与服务端对账，缺口部分增量补拉`；反例 `在 onReconnect 里加了个 for 循环遍历 pendingList`
- 「关键落点地图」是下一个会话最先读的导航，比改动清单更常被用到，别省

## review.md

```markdown
---
plan: <plan-slug>
updated: YYYY-MM-DD
范围: <本轮自查覆盖的改动或提交范围>
---

# 评审

## 未解决

### R-1 <问题标题>

- **严重度**：阻塞 / 重要 / 次要
- **问题**：<具体错在哪>
- **证据**：`path/to/file.ts:88`
- **影响**：<什么场景下产生什么后果>
- **处理方向**：<建议怎么修>
- **关联**：C-2

## 已解决

- **R-2** <问题一句话> → <怎么解决的>，见 C-3
- **R-4** <问题一句话> → 判定为非问题：<理由>

## 已知取舍

- <明确决定不修的问题> — 可接受的原因：<...> — 重新考虑的条件：<...>

## 复查重点

- <下一轮自查优先看什么>
```

**期望**

- 「未解决」每条都有 `file:line` 证据和具体影响，按严重度排序；**说不出影响的问题不要写进来**
- **review.md 不是设计事实源** — 评审结论一旦改变了设计，回写 design.md，这里只留结论
- 「已知取舍」让下一轮自查不再重复报同一个问题，是本文件长期价值最高的部分，压缩时不要动它
- 改动与 design.md 不一致、某条 AC 没有任何测试覆盖，同样构成 `R-n` —— 这两类问题只有对照本目录的文档才发现得了，通用 review 习惯不会替你查
- 外部来源的评审结论（`/code-review`、他人 review）按同样格式落盘即可，不做额外工具编排

## test-design.md

```markdown
---
plan: <plan-slug>
updated: YYYY-MM-DD
---

# 测试方案

## 范围

- 测：<...>
- 不测：<...> — 原因：<...>

## 用例

| ID | 关联 | 层级 | 场景 | 预期 | 落点 | 状态 |
|----|------|------|------|------|------|------|
| T-1 | AC-1 | 单测 | <...> | <...> | `tests/x.test.ts:<name>` | 待实现 / 已实现 |

## 数据与环境

- <fixture / mock / 外部依赖 / 环境前提>

## 手工验证

- [ ] <无法自动化的验证步骤>
```

**期望**

- **只在验证方案本身需要设计时才存在**：并发时序、跨端联调、数据迁移、难以复现的故障、多组合矩阵。普通任务由 `AC-n` 直接覆盖，不建这个文件
- 「不测」和「手工验证」是它不可替代的部分。如果用例表只是在重复测试代码里已有的内容，说明这个文件不该存在

## 反例对照

写文档最容易犯的错，都是把"轨迹"当成"状态"写。

| 反例（轨迹） | 正例（状态） |
|-------------|-------------|
| `原方案是本地缓存，后来改成服务端下发` | `D-3 服务端下发（理由/取舍）` + `已否决方案：本地缓存 → 多端不一致` |
| `2026-08-01 修复了重连丢包；2026-08-03 又修了一次` | `C-2 重连时按 seq 对账补拉缺口` |
| `第一版没考虑空列表，第二版加了判断` | `C-1 …；空列表返回空结果不报错` |
| `已完成：[x] 接口定义 [x] 客户端接入` | （tasks.md 中直接删除这两行） |
| `R-1 已修复（详见下方 5 条讨论）` | `R-1 缺 tenant 过滤 → 已在仓储层补 tenant_id，见 C-4` |
| design.md 里粘贴完整接口签名 | `| 房间快照 | 见落点 | src/room/snapshot.ts:RoomSnapshot |` |
| implementations.md 里粘 20 行代码 | `C-3 …；落点 src/net/reconnect.ts:resync` |
| `需求变更说明：客户要求改为支持多房间` | 直接改写「目标」与相关 `AC-n` |
| 约束里写 `我查了 foo.go，重试上限是 3，所以…` | 约束：`重试上限为 3 → F-2`；findings：`F-2 重试上限为 3 — 依据 foo.go:120` |
| 用户口头说的前提和自己读代码得出的结论混在一节里 | findings.md 分「用户告知」「自行查明」两节，各带自己的依据 |
| agent 自选的方案和用户点头的方案写在同一节 | design.md 分「待拍板」「已确认」两节；用户认可后整条搬家，编号不变 |
