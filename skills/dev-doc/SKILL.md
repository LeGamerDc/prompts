# dev-doc — 开发任务文档维护协议

## 定位

维护 `docs/plans/<plan>/` 下的一组文档，使它们在任意时刻**等于任务的当前状态**：
上下文被清空、换会话、换人接手时，只读这些文档 + 代码就能继续干活。

它只管文档怎么写、什么时候写。它**不管开发怎么进行**。

本 skill 由用户手动加载，不自行判断该不该介入。一旦加载，在本次开发过程中持续生效，直到任务结束或用户另有指示。

### 明确不做的事

- **不控制流程** — 不规定先设计后实现，不设阶段闸门，不要求"确认后才能继续"
- **不盘问需求** — 只记录已经从对话、代码、issue 中识别到的信息；缺失的标注为未确认，不追着用户要
- **不打断协作** — 不要求用户走仪式、不索取审批、不在每次回写后汇报流水
- **不替代 git** — 历史轨迹由 git 承担，文档只表达现在
- **不复制代码** — 文档索引代码，不搬运代码

## 文件职责

一个文件回答一个问题。回答别的问题的内容不属于它。

| 文件 | 回答的问题 | 何时存在 |
|------|-----------|---------|
| `requirements.md` | 这个任务要解决什么问题？做到什么算完成？ | 建 plan 目录时就建 |
| `findings.md` | 关于现状我们查明了什么、凭什么这么认为？ | 出现第一条需要依据的事实时 |
| `design.md` | 为解决它，当前采用什么方案和取舍？ | 出现第一个设计决策时 |
| `tasks.md` | **还剩什么没做？** | 任务不能一口气做完时 |
| `implementations.md` | 改动落在代码的哪里？现在是什么形态？ | 第一组代码改动完成后 |
| `review.md` | 当前改动有哪些问题？哪些已解决、哪些还没有？ | 第一次自查后 |
| `test-design.md` | 怎么验证它是对的？ | 仅当验证方案本身需要设计时 |

跨文件引用用稳定编号，不复述内容：
`AC-n`（验收标准，requirements）、`F-n`（查明的事实，findings）、`D-n`（设计决策，design）、`C-n`（改动单元，implementations）、`R-n`（评审问题，review）、`T-n`（测试用例，test-design）。

## 六条写作铁律

防膨胀的全部力量来自这六条。文档膨胀的根因不是写得多，是**写了轨迹**。

1. **只写现状** — 每句话描述"现在是什么"，不描述"曾经是什么、怎么变成现在这样"。
   禁止出现：原来／之前／最初／后来／改为／第N版/变更记录／更新历史／修订说明。
   例外只有两处：`design.md` 的「已否决方案」和 `review.md` 的「已知取舍」——它们防止后来者重复提同一个被否掉的方案，属于当前状态的一部分。

2. **单一归属** — 一条事实只写在一个文件里，别处用编号引用。
   设计理由不写进 implementations，改动清单不写进 design，问题结论不写进 tasks，
   证据不写进 requirements 和 design——它们只写结论，依据用 `F-n` 指向 findings。

3. **覆盖不追加** — 情况变了就改写原条目，不在后面追加新条目说明它变了。同一主题在同一文件中只能出现一次。

4. **编号稳定** — 编号一经分配不改、不复用；条目删除时编号一起消失，不留空位、不留墓碑。

5. **代码为准** — 文档是代码的索引。文档与代码冲突时，代码是对的，当场改文档，不要反过来"以文档为准"去改代码（除非用户明确说设计还没落地）。

6. **落地即降级** — 已经落进代码的细节，从"描述"降级为"索引"：
   - 接口签名落地后 → design.md 只留 `path/to/file.ts:functionName`，不复制签名
   - 问题修好后 → review.md 从完整条目压成一行结论
   - 任务做完后 → tasks.md 直接删除该行（成果已在 implementations.md）

   文件读起来变吃力时，原因几乎总是该降级的没降级，而不是写太多。

### 图表约定

- **ASCII 图内一律用英文**（节点名、边标签、注释）。中日韩字符在等宽字体下宽度不固定，混进 ASCII 图会让整张图错位。
- 中文解释写在图外，不写进图里。
- 关系复杂到 ASCII 画不清楚时，用表格或 mermaid（mermaid 由渲染器排版，节点文本可以用中文）。

## 维护触发

文档维护由**你刚刚做了什么**触发。不按阶段，不定期巡检，也不因为文件变长才去动它。做完一件事，顺手把对应文档改写成新的现状。

- 用户重新解释或修改了需求 → `requirements.md`
- 用户提出方案或改变了方向 → `design.md`
- 你查明了一个事实（读代码、跑测试、看日志、或用户中途告知）→ `findings.md`
- 你改了代码 → `implementations.md` + `tasks.md`
- 你评审了代码 → `review.md`

几个去向容易写错的时刻：

| 刚刚发生了什么 | 写到哪 |
|--------------|--------|
| 你从代码/issue 推断出需求或约束，用户没确认过 | `requirements.md`「未确认假设」，不混进正文；验证后移入 `findings.md` 或删除 |
| 用户中途告知一个事实（不是需求变更） | `findings.md`「用户告知」 |
| 你读代码/跑测试查明一个事实并据此下了结论 | 结论进 `requirements.md` 或 `design.md`，证据进 `findings.md`「自行查明」，用 `F-n` 连接 |
| 你替用户选了一个方案先往下做 | `design.md`「待拍板」；用户认可后整条搬到「已确认」 |
| 某个方案被明确否掉 | `design.md`「已否决方案」一行 |
| 实施时偏离了原设计 | 先改 `design.md`（它必须始终等于当前打算），再在 `implementations.md`「与设计的偏差」留一行 |
| 你判定某个问题不修 | `review.md`「已知取舍」，写清可接受的原因 |
| 对话要中断 / 交回控制权 | `tasks.md`「进行中」，写清做到哪、下一步的具体动作 |

判断标准：**如果这条信息丢了，下一个会话会走弯路，就写下来；否则不写。**

## plan 目录

### 何时创建

本 skill 被加载本身就说明当前任务需要这套文档——任务在 `docs/plans/` 下还没有目录时，直接建。
会话中夹带的琐事（改个拼写、跑个命令、回答提问）不属于任务本身，不为它建 plan。

### 命名与定位

- 目录名 kebab-case，短且自解释：`docs/plans/room-reconnect/`
- 定位当前 plan 的优先级：用户提到的 > 与当前分支名匹配的 > `docs/plans/` 下最近修改的
- 拿不准是新 plan 还是老 plan 的延续时，问一句，别猜着建

### 接手已有 plan

本 skill 被加载时，如果要做的任务在 `docs/plans/` 下已有文档（续作、或换了会话）：

1. 按顺序读：`requirements.md`（要做什么）→ `design.md`（怎么做）→ `tasks.md`（还剩什么）→ `review.md`（有什么坑）→ `implementations.md`（代码在哪）；
   `findings.md` 的「用户告知」一节必读——这些事实无法从代码重建；「自行查明」按需，被 `F-n` 引用时再读
2. 抽查 `implementations.md` 里 1-3 个落点，确认文档与代码一致；不一致按铁律 5 当场修文档
3. 用 3-5 行复述任务目标 / 已经到哪 / 仍在「待拍板」的 `D-n` / 接下来打算做什么，然后直接继续干活，不等确认（除非文档与代码严重脱节，或存在阻塞性未确认假设）

## 两个特殊时刻

日常维护不需要流程：文档任何时候和现实对不上，就地改，以现实为准。以下两件事例外，因为默认不这么做就会出错。

**为已经做了一半的工作补建文档**（中途才建 plan 目录、或接手别人的改动）：
只从当前代码和 `git diff` 反推"现在是什么形态"，**不要还原历史，不要为反推不出的决策编造理由** —— 不确定的标注为「推断」，或留进「未确认假设」等后续对话补上。目标是"下次能接上"，不是"补出一份完整的设计文档"。

**任务收尾**（tasks.md 清空且 review 无未解决项）：
把长期有效的结论**回流到项目长期文档** —— 新约定与踩坑结论进常驻指令文件（`CLAUDE.md` / `AGENTS.md`）或规范文档，稳定的架构决策进架构文档，`findings.md` 逐条过一遍、长期有效的事实进项目知识索引（按问题命名文件的目录：repo 已有就用它，没有就建 `docs/knowledge/`），plan 里只留一行指向。plan 文档是任务级的，会随任务过期，不回流就等于丢了。然后 `requirements.md` 的 `status` 改为已完成，删除 `tasks.md`。
